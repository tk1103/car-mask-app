# 20回制限エラー調査（一昨日以降未使用なのに「今日」制限に達する事象）

## 調査結果

### 1. 日付の基準が **UTC** になっている（最も有力な原因）

- **該当コード**: `getTodayDateString()`（route.ts 32–34行目）
  ```ts
  function getTodayDateString(): string {
    return new Date().toISOString().slice(0, 10);  // UTC の YYYY-MM-DD
  }
  ```
- **挙動**: 「1日」のリセットは **UTC 0:00**。
  - 日本（JST = UTC+9）では **毎朝 9:00** に「日付」が切り替わる。
  - 例: 日本時間 2/11 08:00 → UTC ではまだ 2/10 → サーバーは「2/10」としてカウント。
- **起きうる状況**:
  - 「昨日」日本時間で全く使っていなくても、**UTC ではまだ「昨日」** のままの時間帯（日本時間 0:00〜8:59）に撮影すると、サーバーは「昨日」のカウントで判定する。
  - 逆に、**日本時間で「昨日」使った 20 回** が、UTC では「今日」にまたがっていると、**日本時間の「今日」の朝まで** 制限が続いて見える。

→ **「一昨日以降撮影していない」のに「今日」制限になる** のは、  
「今日」が日本時間の今日でも、サーバー側はまだ UTC の「前日」とみなしている時間帯である可能性が高い。

### 2. 日次カウントの保存が **メモリ（Map）のみ**

- **該当**: `dailyLimitStore = new Map<string, { count: number; date: string }>()`（16行目）
- **挙動**: Vercel などのサーバーレスではインスタンスごとにメモリが分かれる。
  - 同じインスタンスに当たり続けると、そのインスタンス内の「今日」カウントが 20 になるまで増える。
  - 日付は **毎リクエスト** `getTodayDateString()` で計算するため、UTC が変われば `entry.date !== today` でリセットされる。
- **結論**: 「日付がずれて見える」原因は、主に上記の **UTC 日付** によるものと考えられる。メモリの永続化有無は、同じインスタンスに当たる限りは日付ロジックどおりに動く。

### 3. カウントが増えるタイミング

- **該当**: POST ハンドラ内で `incrementDailyCount(clientId)` を 1 回だけ実行（289行目）。
- **撮影フロー**: クライアントは「残数確認の GET」→「解析の POST」の順で呼ぶ。GET ではカウントは増やしていない。
- **結論**: 1 回の撮影 = 1 回の POST = 1 回の加算。二重カウントや誤って増える経路は見当たらない。

### 4. クライアント識別

- デバイス単位: `X-Device-Id` ヘッダ（localStorage の UUID 等）。
- 未送信時: IP（`x-forwarded-for` / `x-real-ip`）で識別。
- 同じデバイス・同じ IP なら、サーバーが持つ「今日」カウントが 20 に達すると制限になる。

---

## 結論（原因となる事象）

1. **日付のリセットが UTC 0:00 であること**  
   → 利用者の「今日」とサーバーの「今日」が最大で約 1 日ずれる（日本時間では毎朝 9:00 にリセット）。
2. 上記のため、**「一昨日以降使っていない」と感じていても、サーバー上では「昨日」のカウントが残っている時間帯に「今日」撮影した** と判定され、20回制限になることがある。

---

## 推奨対策

1. **日付を JST（Asia/Tokyo）で計算する**  
   - `getTodayDateString()` で UTC ではなく `Asia/Tokyo` の「今日」の `YYYY-MM-DD` を使う。
2. または **リセット時刻を明示する**  
   - 例: 「1日のリセットは日本時間 9:00 です」と UI やヘルプに表示する。
3. （必要なら）**永続ストアの導入**  
   - 現状はメモリのみのため、インスタンスが冷えるとカウントは消える。挙動を安定させたい場合は Redis 等で日次カウントを保存する方法を検討する。

以上が、一昨日以降撮影していないのに今日 20 回制限になる事象の調査結果と原因・対策です。
